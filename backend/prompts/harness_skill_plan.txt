Candidate schema constraints:
- Each candidate object must contain ONLY these keys:

- skill_type must be exactly one of: "guide", "skeleton", "both".
  - "guide": the skill's reusable value is process/adaptation guidance and validation checklists — no generalizable automation code logic is being extracted.
  - "skeleton": the skill's reusable value is a config-driven code template that generalizes the asset's core automation logic (e.g., session handling, download-event handling, per-row status tracking, retry scaffolding) so only portal-specific selectors/URLs/mappings need to be swapped in.

- Do not include applicable_scenarios, recommended_scripts, scores, score_breakdown, target_users, expected_outputs, source_evidence, original_asset_reference, risk_level, or other extra keys inside candidates.
- Keep candidate objects compact enough for UI display and downstream skill generation.

reference_files requirements:

- Reward candidates whose implementation and validation steps are clear from the asset/repository.
